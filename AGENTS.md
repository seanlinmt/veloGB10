# AGENTS.md

Rust + CUDA LLM inference engine for NVIDIA GB10 (DGX Spark, sm_121). Single crate `gb10_inference` (src/), CUDA kernels in `kernels/*.cu` compiled to PTX by `build.rs` into `src/ptx/`, C RDMA shim in `native/net_shim.c`. No CI, no lint config. Tests are Rust integration tests in `tests/`, plus a few Python reference generators (see Testing below).

## Build

```bash
cargo build --release   # needs nvcc (CUDA_HOME honored) + libibverbs-dev; builds PTX too
cargo test              # tests are plain cargo; GPU tests need a GB10 present
cargo test <name>       # single test
```

## Testing quirks

- Tests that need model/fixture dumps generated by Python (`dsv4_cpu_ab_test`, `dflash2_oracle_test`, `dspark_oracle_test`, `hy3_load_test`, etc.) **skip silently** when the prerequisites are absent, so `cargo test` passing full-green does not mean everything ran. Prerequisites are documented as doc-comments at the top of each test file (e.g. `python3 scripts/dsv4_tiny_ab.py --out /tmp/dsv4_tiny_ab`, needs torch).
- `tests/tokenize_endpoint_test.py` and `tests/model_load_graceful_exit_gate.sh` are live-server checks against a running instance, not cargo tests.

- **Build fails loudly if nvcc fails**; on a machine without nvcc it silently falls back to the *checked-in* PTX in `src/ptx/` with only a warning — on a CUDA box, don't trust such a build for kernel work.
- **The binary is not self-contained.** It loads `src/ptx/*.ptx` relative to its working directory — run it from the repo root (or a dir containing `src/ptx/`). A build-fingerprint handshake (`KERNEL_BUILD_ID` hashed over kernel sources, baked into both binary and PTX) refuses mismatched binary/PTX pairs at startup.
- Adding a new `.cu` runtime module requires editing the `kernels` list in `build.rs` — only modules listed there are compiled into the serving manifest. Note the arch per file: most are `sm_121`, but the `mxf4nvf4` OMMA users (`mxfp4_*`, `gpu_w4a4`) must be `sm_121a` (plain sm_121 rejects those instructions).
- `gpu_batch.cu` `#include`s `native/tp_doorbell.h` (shared TP=2 wire layout with `net_shim.c`) — the build hash covers it, so change both files in lockstep.

## No env vars — ever

The engine reads **no environment variables**. Every option is a CLI flag; a set `GB10_*`/`RUST_INFER_*` variable **refuses startup** and names the replacement flag. Full removed-var → flag table: `docs/ENV_TO_FLAGS.md`. `--print-config` prints resolved values for a given command line.

## Running / debugging

- Known-good launch lines: `BEST_WAYS_TO_RUN.md` (start there); model bring-ups: `QWEN_27B_SETUP.md`, `QWEN_38_FLASH_NEXT_SETUP.md`, `HY3_SETUP.md`.
- TP=2/TP=4: start `./gb10_inference --node --port 29500` on peers **first**; do not copy models to peers — the head ships per-rank shards at sync (cache: `~/.cache/gb10_tp/`, see `MANAGING_CACHE.md`).
- Two coupled flags: `--kv-cache k8v8` is rejected with `--max-batch > 1` (int8 K/V rows only read by the single-lane attention kernel); use `--kv-cache bf16`/`k8v4` for concurrency. Qwen3.8 27B needs a drafter: `--spec-source dflash2 --draft-dir <dir>`.
- Server ready line: `OpenAI-compatible server running on http://0.0.0.0:<port>`; `[head] <ip> (rank N) READY` per node on TP runs.
- Diagnostic probes exist without a model: `--net-test`, `--tp-barrier-bench`, `--probe-bandwidth` (~255 GB/s expected on idle GB10), plus `--probe-*`/`--bench-*` for specul­ation/GEMM/kernels (full list in README "Probes").

## Hard invariants (don't break these)

- **Bitwise-lossless speculation**: greedy output must be bit-identical with and without speculation; batch-invariant GEMMs are what guarantee it (verify of width N == N separate decodes). Any change to GEMM shapes/quality that breaks this is a correctness regression.
- **TP ranks lockstep**: every decode step is hash-checked across ranks and aborts loudly on divergence. Debug desync with `--tripwire`, `--tp-agree-drill`, `--tp-tail-drill`.
- `serde_json` and `minijinja` must keep the `preserve_order` feature — tool-call `<tools>` rendering must byte-match transformers/vLLM insertion order (there's a comment in `Cargo.toml` explaining a past failure; don't "clean it up").
- Docs claim only measured numbers; correctness gates (LOSSLESS_OK, batch invariance, TP byte-identity) are the release contract.

## Repo hygiene quirks

Working tree contains committed-mess-looking stray logs (`head_server.log*`, `node_ai2.log*`) and an untracked binary `gb10_inference` — don't delete or "clean" them; they're runtime residue, not content. Launch helpers in `scripts/` (`run_tp_node.sh`, `run_tp_server.sh`, `launch_qwen38_flash_next.sh`) are the maintained ways to bring up nodes.
